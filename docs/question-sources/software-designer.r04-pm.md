# 软件设计师（中级）强化训练（下午题专项）

## P4.1 数据流图：元素、画图规则与常见错误

数据流图（DFD）由外部实体、加工、数据流和数据存储四种元素组成。外部实体是系统之外的人、组织或其他系统，用矩形表示；加工用圆或圆角矩形表示，名称是动词短语；数据流用带箭头的线表示，名称是名词短语；数据存储用两条平行线表示，存放需要保存的数据。画图规则：数据流必须至少有一端是加工，即外部实体与外部实体之间、外部实体与数据存储之间、数据存储与数据存储之间不能直接有数据流；每个加工至少有一个输入数据流和一个输出数据流，只有输出没有输入称为“奇迹”，只有输入没有输出称为“黑洞”；流入数据存储的数据流表示写入，从数据存储流出的数据流表示读取；同一个数据存储可以被多个加工读写。顶层图（环境图）只有一个加工，代表整个系统，反映系统与外部实体之间的输入输出，顶层图中通常不画数据存储。数据流图只表示数据的流动，不表示控制流和处理的先后顺序，也不表示物理实现。

## P4.2 分层数据流图与父子图平衡

分层数据流图从顶层图（0 层图）开始逐层细化：顶层图只有一个加工，下一层图把该加工分解为若干子加工，加工按层次编号，例如加工 2 的子加工编号为 2.1、2.2、2.3。父图与子图的平衡是指子图的输入输出数据流必须与父图中对应加工的输入输出数据流保持一致：父图中该加工的每个输入、输出数据流都要出现在子图中，子图也不能凭空增加父图中没有的外部输入输出数据流。子图内部加工之间的数据流，以及只被子图内部加工使用的数据存储，不需要在父图中出现。分解时子加工数量不宜过多，一般不超过 7 个，否则图会过于复杂。分解到不能再分的基本加工，用判定表、判定树或结构化语言描述加工逻辑。分层的目的是控制复杂度，使分析人员自顶向下逐步求精。

## P4.3 数据流图案例：从说明到图的解题套路

解题方法：先圈出说明中的人、组织和其他系统，作为外部实体；再把动词短语对应为加工；把“保存、记录、登记、查询”的对象作为数据存储；然后为每个加工梳理输入和输出，检查是否有加工只有输入或只有输出；最后根据说明补全遗漏的数据流，写清它的来源和去向。判断数据流方向的经验：“登记订单”需要写入订单表，即加工指向数据存储；“查询库存”需要读取库存表，即库存表指向加工；某外部实体既要向系统发送数据又要接收结果时，应分别画出方向相反的两条数据流。数据存储通常以“表”“档案”“库”命名，如订单表、顾客档案、库存表。外部实体通常是顾客、管理员、供应商、银行、仓库、教师、学生等；仅是系统的操作者的“管理员”“员工”，也属于外部实体。数据流命名要体现数据内容，如订单信息、库存信息、支付结果、发货单、审核结果等，不要用“审核”“处理”这类动词。

## P4.4 数据字典：条目与定义符号

数据字典是对数据流图中所有数据元素的定义集合，条目分为数据流、数据项、数据存储、加工等。数据字典中定义数据结构时使用的符号：等号 = 表示“定义为”或“由……组成”；加号 + 表示“与”，连接并列的数据项；方括号 [ ] 中用竖线 | 分隔，表示“或”，即选择其中之一；花括号 { } 表示重复，可以在右上、右下标注重复次数的上限和下限；圆括号 ( ) 表示可选，即该项可有可无；星号 * 括起来的内容是注释。例如：订单 = 订单号 + 日期 + 客户 + {商品编号 + 数量}，表示订单由订单号、日期、客户以及重复出现的商品条目组成；支付方式 = [现金 | 刷卡 | 转账]，表示三者选一；地址 = 省 + 市 + (邮编)，表示邮编可有可无。数据字典与数据流图配合，共同构成系统的逻辑模型。

## P4.5 E-R 图案例：联系类型判断与属性归属

E-R 图的基本元素：实体用矩形表示，属性用椭圆表示，联系用菱形表示。联系的类型有一对一（1:1）、一对多（1:n）和多对多（m:n）。判断联系类型的方法：分别从两端提问“一个 A 对应几个 B”和“一个 B 对应几个 A”，两端都是“多”则是 m:n，一端是“一”另一端是“多”则是 1:n，两端都是“一”则是 1:1。联系也可以有属性，如“选修”联系的属性成绩，必须由学生和课程两端共同决定，因此要放在联系上。常见案例：部门与员工是 1:n，学生与课程是 m:n，班级与班主任是 1:1，读者与图书（借阅）是 m:n，商品与订单（订单明细）是 m:n，病人与医生（就诊）是 m:n。弱实体依赖于其他实体而存在，其主键包含所依赖实体的主键。多值属性通常需要单独建立关系；复合属性由多个简单属性组成。三元联系涉及三个实体，如供应商、零件、项目之间的供应联系，转换成关系模式后主键通常为三个实体主键的组合。

## P4.6 E-R 图转关系模式：主键、外键的确定

E-R 图转换为关系模式的规则：每个实体转换为一个关系模式，实体的属性成为关系的属性，实体的主键成为关系的主键。1:1 联系可以合并到任意一端实体的关系中，并加入对方的主键作为外键；1:n 联系把 1 端实体的主键作为外键加入 n 端实体的关系；m:n 联系必须转换为独立的关系模式，其属性由两端实体的主键（作为外键）和联系自身的属性组成，主键通常是两端主键的组合。例如员工（员工号，姓名，部门号）中，部门号是外键，参照部门（部门号，部门名）的主键；选修（学号，课程号，成绩）的主键是（学号，课程号），学号和课程号分别是外键。关系模式书写时主键加下划线，外键用波浪线或虚线标出。判断外键的方法：某属性是另一个关系的主键，但在本关系中不是主键，或只是组合主键的一部分。数据库设计分为需求分析、概念设计（E-R 图）、逻辑设计（关系模式）、物理设计和实施维护。

## P4.7 规范化案例与 SQL 要点

关系模式规范化：1NF 要求属性不可再分；2NF 在 1NF 基础上消除非主属性对候选键的部分函数依赖；3NF 在 2NF 基础上消除非主属性对候选键的传递函数依赖；BCNF 要求每个函数依赖的决定因素都包含候选键。案例分析方法：先写出函数依赖，求出候选键，再检查：若候选键是组合键，且某非主属性只依赖于其中一部分，则存在部分依赖，不满足 2NF；若非主属性 C 依赖于非主属性 B，B 依赖于候选键 A，则 C 对 A 传递依赖，不满足 3NF。分解时，把引起部分依赖或传递依赖的属性分出去形成新的关系，例如订单（订单号，客户号，客户名）存在订单号→客户号→客户名的传递依赖，应分解为订单（订单号，客户号）和客户（客户号，客户名）。无损连接分解要求分解后的关系通过自然连接能还原出原关系；保持函数依赖要求原关系的函数依赖在分解后的关系中仍然成立。SQL 要点：SELECT 列 FROM 表 WHERE 条件 GROUP BY 分组列 HAVING 分组条件 ORDER BY 排序列；WHERE 在分组前过滤行，HAVING 在分组后过滤组；外键用 FOREIGN KEY (列) REFERENCES 表(列) 定义，主键用 PRIMARY KEY 定义。

## P4.8 UML 用例图案例：参与者、包含与扩展

用例图包含参与者、用例和系统边界。参与者是与系统交互的人、设备或其他系统，画在系统边界之外；用例是参与者通过系统要完成的一个有价值的目标，用椭圆表示，名称是动宾短语。参与者与用例之间用关联（实线）连接。用例之间的关系：包含（include）表示基用例的执行必然要调用被包含用例，被包含用例是公共子流程，虚线箭头由基用例指向被包含用例；扩展（extend）表示在特定条件下基用例才可能执行扩展用例，扩展用例是可选行为，虚线箭头由扩展用例指向基用例；泛化表示一般与特殊的关系，子用例继承父用例的行为，参与者之间也可以泛化。例如“下单”必须先执行“验证登录”，用包含；“下单”过程中如果用户有优惠券才执行“使用优惠券”，用扩展。补全用例图的思路：先找出参与者，即谁在使用系统；再为每个参与者找出它的目标；最后识别公共的、必须的子流程（include）和有条件的可选流程（extend）。常见误区：把系统内部的功能步骤当作参与者，或把操作步骤拆得过细而成为用例。

## P4.9 UML 类图案例：类间关系与多重度

类图中类用三层矩形表示：类名、属性、方法；可见性符号 + 表示 public，- 表示 private，# 表示 protected。类之间的关系：泛化（继承）用带空心三角箭头的实线，指向父类；实现用带空心三角箭头的虚线，指向接口；关联用实线（可带箭头表示单向导航）；聚合表示整体与部分关系，部分可以独立于整体存在，用空心菱形，菱形画在整体一端；组合也是整体与部分关系，但部分不能脱离整体，二者生命周期一致，用实心菱形，菱形画在整体一端；依赖用带箭头的虚线，表示一个类使用另一个类，如方法参数或局部变量。多重度：1 表示恰好一个，0..1 表示零个或一个，* 或 0..* 表示零个或多个，1..* 表示一个或多个。例如一个订单包含一个或多个订单项，订单一端的多重度为 1，订单项一端为 1..*；订单与订单项是组合关系，订单删除时订单项一并删除；学校与教师是聚合关系。抽象类和抽象方法的名称用斜体表示，接口用 <<interface>> 构造型标注。

## P4.10 UML 动态图案例：状态图、活动图与顺序图

状态图描述一个对象在生命周期内的状态，以及状态之间由事件触发的转换。状态图的元素：初始状态（实心圆，只有出口）、终止状态（带圈的实心圆，只有入口）、状态（圆角矩形）、转换（带箭头的线，标注为 事件[条件]/动作）。状态图适合描述单个对象在不同事件下的行为变化，如订单的待支付、已支付、已发货、已完成、已取消等状态。活动图描述业务流程或操作的步骤，元素包括开始、结束、活动（动作）、判定（菱形，有条件分支）、分叉与汇合（粗横线，表示并行），泳道用于划分责任。顺序图强调对象之间消息传递的时间顺序，对象沿水平方向排列，生命线垂直向下，时间自上而下；同步消息用实心箭头，发送者等待返回；异步消息用开放箭头；返回消息用虚线箭头；激活条表示对象正在执行。通信图（协作图）强调对象之间的链接和消息的组织结构，用序号表示消息顺序，与顺序图可以相互转换。下午题补全状态图时，要根据说明找出所有状态和触发事件；补全顺序图时，要根据说明的先后步骤补充消息和参与对象。

## P4.11 C 语言基础：指针、传参、字符串与宏

C 语言基础（下午算法题常用）：数组下标从 0 开始，二维数组按行存储；数组名是首元素的地址，a[i] 等价于 *(a + i)；指针变量保存地址，通过解引用 * 访问所指内容，指针加 1 移动一个所指类型的大小。函数参数默认按值传递，函数内修改形参不会影响实参，要修改实参必须传递指针（地址）。字符串以空字符 '\0' 结尾，因此存放 n 个字符的字符串至少需要 n + 1 个字节；sizeof 数组名得到数组的总字节数，strlen 得到不含结尾空字符的长度。整数除法的结果向零取整，如 7 / 2 = 3，-7 % 3 = -1。i++ 先使用 i 的值再加 1，++i 先加 1 再使用。宏定义只做文本替换，不加括号容易出错，如 #define SQ(x) x*x，SQ(2+3) 展开为 2+3*2+3，结果是 11。switch 语句中 case 若没有 break 会继续执行下一个 case，称为穿透。static 局部变量在函数调用之间保持原值，只初始化一次。结构体指针用 p->x 访问成员，等价于 (*p).x。用 malloc 申请的堆内存必须用 free 释放，否则造成内存泄漏；释放后应将指针置为 NULL，避免悬空指针。

## P4.12 读程序题：递归、循环与常见递归函数

读程序题的方法：手工跟踪变量的变化，列出每次循环或递归调用时各变量的值。递归函数由递归出口和递归体组成，每次调用都要保存现场，递归深度过大会导致栈溢出。经典递归：阶乘 f(n) = n × f(n-1)，f(0) = 1；斐波那契 fib(n) = fib(n-1) + fib(n-2)，fib(1) = fib(2) = 1，朴素递归的时间复杂度是指数级；最大公约数 gcd(a, b) = gcd(b, a mod b)，gcd(a, 0) = a，称为辗转相除法；汉诺塔 n 个盘子至少需要 2^n - 1 次移动；二分查找每次把区间减半，时间复杂度为 O(log n)；两层循环嵌套，若内层循环变量从外层变量开始，总执行次数为 n(n+1)/2，量级仍是 O(n²)；循环变量每次乘 2，执行次数约为 log2 n。判断素数只需测试到 √n。把整数各位拆开用 n % 10 取个位，用 n / 10 去掉个位。

## P4.13 分治策略与排序、查找算法填空要点

分治法把问题分解为若干规模较小、相互独立的同类子问题，递归求解后再合并，典型有归并排序、快速排序、二分查找、大整数乘法、Strassen 矩阵乘法、棋盘覆盖。分治算法的时间复杂度常用递推式 T(n) = aT(n/b) + f(n) 分析：归并排序 T(n) = 2T(n/2) + O(n)，结果为 O(n log n)；二分查找 T(n) = T(n/2) + O(1)，结果为 O(log n)；Strassen 算法把 8 次子矩阵乘法减为 7 次，T(n) = 7T(n/2) + O(n²)，结果约为 O(n^2.81)；快速排序平均 O(n log n)，最坏 O(n²)。快速排序的划分过程：取第一个元素为基准，从右向左找小于基准的元素放到左边的空位，再从左向右找大于基准的元素放到右边的空位，直到两个指针相遇，把基准放到相遇位置，此时基准左边的元素都不大于它，右边的都不小于它；随后只递归处理基准左右两个子区间，基准位置不再参与排序。快速排序在序列已有序且总取第一个元素为基准时退化为 O(n²)。归并排序合并两个有序序列时需要 O(n) 的辅助数组，比较两个序列的当前元素，较小者先放入结果，该排序是稳定的。二分查找要求有序数组，mid = (low + high) / 2，若 a[mid] < key 则 low = mid + 1，若 a[mid] > key 则 high = mid - 1。棋盘覆盖：2^k × 2^k 的棋盘有一个特殊方格，用 L 型骨牌覆盖其余方格，需要 (4^k - 1) / 3 块骨牌。同时求最大值和最小值用分治，约需 3n/2 - 2 次比较。

## P4.14 动态规划：递推式、填表与典型问题

动态规划适用于具有最优子结构和重叠子问题的问题，用表格保存子问题的解以避免重复计算，通常自底向上填表。0-1 背包：dp[i][w] 表示前 i 件物品、背包容量为 w 时的最大价值，递推式为 dp[i][w] = max(dp[i-1][w], dp[i-1][w-wi] + vi)，当 w < wi 时 dp[i][w] = dp[i-1][w]；时间复杂度 O(nW)，空间可压缩为一维数组，压缩后容量要从大到小遍历。最长公共子序列（LCS）：当 xi = yj 时 c[i][j] = c[i-1][j-1] + 1，否则 c[i][j] = max(c[i-1][j], c[i][j-1])，时间复杂度 O(mn)。矩阵链乘：m[i][j] = min(m[i][k] + m[k+1][j] + p(i-1) × p(k) × p(j))，k 取 i 到 j-1，时间复杂度 O(n³)。最长递增子序列：dp[i] = max(dp[j] + 1)，其中 j < i 且 a[j] < a[i]，时间复杂度 O(n²)。硬币找零（最少硬币数）：dp[v] = min(dp[v - c] + 1)。数塔问题自底向上，dp[i][j] = a[i][j] + max(dp[i+1][j], dp[i+1][j+1])。动态规划与分治的区别：分治的子问题相互独立，动态规划的子问题相互重叠。

## P4.15 贪心、回溯与分支限界

贪心算法每一步都做出当前看来最优的选择，不回溯，适用于具有贪心选择性质和最优子结构的问题，如活动安排（按结束时间从早到晚排序，依次选择与已选活动不冲突的活动）、部分背包（按单位重量价值从大到小装入）、哈夫曼编码、Prim 与 Kruskal 最小生成树、Dijkstra 最短路径。0-1 背包不能用贪心求最优解，部分（分数）背包可以。回溯法用深度优先方式搜索解空间树，遇到不满足约束的结点就剪枝并回退，典型问题有 n 皇后、图的着色、0-1 背包、子集和、哈密顿回路；解空间树分为子集树（每个元素选或不选，叶子数 2^n）和排列树（叶子数 n!）两类。分支限界法用广度优先或最小耗费优先方式搜索解空间树，每个活结点只有一次扩展机会，用限界函数剪枝，通常用队列或优先队列保存活结点，适合求最优解，典型问题有 0-1 背包、旅行商、单源最短路径、任务分配。回溯法与分支限界法的区别：回溯法求出所有解或某一个解，深度优先；分支限界法求一个最优解，广度优先或最小耗费优先。n 皇后问题用回溯，约束是任意两个皇后不在同一行、同一列、同一对角线上；4 皇后有 2 个解，8 皇后有 92 个解。

## P4.16 算法设计策略的识别与复杂度速查

判断算法设计策略的线索：问题可以分解为相互独立的同类子问题，且子问题的解可以合并，用分治；子问题重叠，求最优值（最大价值、最短、最少、方案数），用动态规划；每一步有明显的局部最优选择且可证明不影响全局最优，用贪心；要枚举所有可能或满足约束的全部方案，如排列、组合、棋盘布局，用回溯；在解空间树中求最优解且能计算上下界进行剪枝，用分支限界。复杂度速查：归并排序 O(n log n)；快速排序平均 O(n log n)；0-1 背包动态规划 O(nW)；最长公共子序列 O(mn)；矩阵链乘 O(n³)；Prim 算法 O(n²)；Dijkstra 算法 O(n²)；Floyd 算法 O(n³)；活动安排贪心 O(n log n)，主要花在排序上；哈夫曼编码 O(n log n)；n 皇后回溯最坏为指数级。下午题中常要求写出算法所采用的设计策略并说明理由，典型回答是：该问题具有最优子结构且子问题重叠，故采用动态规划。

## P4.17 设计模式案例（一）：创建型模式的场景识别

创建型模式关注对象的创建过程。单例（Singleton）保证一个类只有一个实例并提供全局访问点，构造函数私有，通过静态方法获取实例，如配置管理器、日志对象、线程池。工厂方法（Factory Method）定义创建对象的接口，由子类决定实例化哪个类，Creator 声明工厂方法，ConcreteCreator 返回 ConcreteProduct，如不同类型文档的创建。抽象工厂（Abstract Factory）提供一个接口，用来创建一系列相关或相互依赖的对象（产品族）而无需指定具体类，如 Windows 风格和 Mac 风格的按钮与文本框；增加新的产品族容易，增加新的产品种类困难。生成器（Builder）把复杂对象的构建与表示分离，同样的构建过程可以创建不同的表示，由 Director 控制构建步骤，Builder 定义各步骤的接口，如组装不同配置的电脑。原型（Prototype）用原型实例指定创建对象的种类，通过复制（克隆）已有对象来创建新对象，如复制已有图形再修改，避免重复初始化的开销。工厂方法针对一个产品等级结构，抽象工厂针对多个产品等级结构（产品族）。

## P4.18 设计模式案例（二）：结构型模式的场景识别

结构型模式关注类和对象的组合。适配器（Adapter）把一个类的接口转换成客户期望的另一个接口，使原本接口不兼容的类可以一起工作，如让旧系统接口兼容新系统。桥接（Bridge）把抽象部分与实现部分分离，使二者可以独立变化，如形状与颜色组合时避免类的数量爆炸。组合（Composite）用树形结构表示整体与部分，使客户对单个对象和组合对象一致对待，如文件夹与文件、公司的部门与员工。装饰器（Decorator）动态地给对象添加额外职责，比继承更灵活，如给咖啡动态加奶、加糖。外观（Facade）为子系统中的一组接口提供一个统一的高层接口，使子系统更易使用，如一键启动整个家庭影院。享元（Flyweight）运用共享技术有效地支持大量细粒度对象，节省内存，如文字编辑器中大量重复的字符对象。代理（Proxy）为其他对象提供一个代理以控制对它的访问，常见有远程代理、虚代理（延迟创建开销大的对象）、保护代理（控制访问权限）。

## P4.19 设计模式案例（三）：行为型模式的场景识别（一）

行为型模式关注对象之间的职责分配与交互。责任链（Chain of Responsibility）让多个对象都有机会处理请求，沿链传递直到被处理，发送者与接收者解耦，如请假审批逐级上报。命令（Command）把请求封装成对象，支持请求排队、记录日志和撤销，Invoker 调用 Command，Command 调用 Receiver，如遥控器按钮、编辑器的撤销功能。解释器（Interpreter）为语言定义文法并用解释器解释句子，如正则表达式、四则运算表达式。迭代器（Iterator）顺序访问聚合对象的元素而不暴露其内部表示，如遍历集合。中介者（Mediator）用一个中介对象封装一组对象之间的交互，使对象不必相互引用，把网状关系变成星状，如聊天室、机场塔台。备忘录（Memento）在不破坏封装的前提下捕获并保存对象的内部状态，以便以后恢复，如游戏存档；备忘录模式有 Originator（原发器）、Memento（备忘录）、Caretaker（管理者）三个角色。

## P4.20 设计模式案例（四）：行为型模式的场景识别（二）

观察者（Observer）定义对象之间一对多的依赖，当一个对象的状态改变时，所有依赖它的对象都得到通知并自动更新，Subject 维护观察者列表，如订阅发布、事件监听、气象站。状态（State）允许对象在内部状态改变时改变其行为，把与状态相关的行为封装到状态类中，消除庞大的条件分支，如订单状态、TCP 连接状态。策略（Strategy）定义一系列算法，把它们封装起来并使它们可以互换，Context 持有 Strategy，如不同的排序策略、折扣策略、支付方式。模板方法（Template Method）在父类中定义算法的骨架，把某些步骤延迟到子类中实现，子类不改变算法结构即可重定义特定步骤，如固定流程的数据处理。访问者（Visitor）表示一个作用于对象结构中各元素的操作，使得不改变元素类就可以定义新的操作，适用于元素类稳定而操作经常变化的场合，其核心是双分派。状态与策略结构相似，区别在于：状态由对象内部状态变化自动切换，策略由客户端选择。

## P4.21 设计模式案例（五）：从参与者名称反推模式

常考的参与者名称：Singleton 只有一个类；Factory Method 的 Creator、ConcreteCreator、Product、ConcreteProduct；Abstract Factory 的 AbstractFactory、ConcreteFactory、AbstractProduct；Builder 的 Director、Builder、ConcreteBuilder、Product；Prototype 的 Prototype、ConcretePrototype、Client；Adapter 的 Target、Adaptee、Adapter；Bridge 的 Abstraction、RefinedAbstraction、Implementor；Composite 的 Component、Leaf、Composite；Decorator 的 Component、ConcreteComponent、Decorator、ConcreteDecorator；Facade 的 Facade 与子系统类；Flyweight 的 Flyweight、FlyweightFactory；Proxy 的 Subject、RealSubject、Proxy；Chain of Responsibility 的 Handler、ConcreteHandler；Command 的 Command、ConcreteCommand、Invoker、Receiver；Iterator 的 Iterator、Aggregate；Mediator 的 Mediator、Colleague；Memento 的 Originator、Memento、Caretaker；Observer 的 Subject、Observer；State 的 Context、State；Strategy 的 Context、Strategy；Template Method 的 AbstractClass、ConcreteClass；Visitor 的 Visitor、Element、ObjectStructure。看到某组参与者名称，即可反推出设计模式。

## P4.22 设计模式案例（六）：C++ 与 Java 实现要点

C++ 与 Java 实现要点：单例模式中构造函数私有，用静态成员保存唯一实例，通过静态方法获取实例；Java 的饿汉式单例在类加载时就创建实例，天然线程安全，懒汉式在第一次使用时才创建，多线程下需要同步（synchronized）。Java 用 interface 定义接口，用 implements 实现接口，用 extends 继承类，抽象类用 abstract 修饰。C++ 中含有纯虚函数（如 virtual void f() = 0;）的类是抽象类，不能实例化；基类的析构函数应声明为 virtual，以便通过基类指针删除派生类对象；子类重写虚函数时可以加 override 关键字；要通过基类指针或引用实现多态，被调用的函数必须是虚函数，否则按指针的静态类型调用基类版本。装饰器和代理都持有被包装对象的引用，并实现与它相同的接口：装饰器侧重增加职责，代理侧重控制访问。工厂方法中，Creator 的工厂方法返回 Product 类型，子类重写它以返回具体产品。观察者模式中，Subject 保存观察者列表，状态变化时遍历列表，调用每个观察者的 update 方法。策略模式中，Context 持有 Strategy 的引用，通过组合而不是继承来替换算法。模板方法的骨架方法在 Java 中通常用 final 修饰，防止子类改变算法结构。
