# 改造方案：每日目标与提醒 · 按知识点刷题 · 题库内搜索 · 反馈处理 · 错题本分题库

> 日期：2026-10-05　状态：**已实现**（五项都做完，带测试；与方案的差异见 §9）
> 范围：服务端（Go）、管理后台（Vue）、H5 客户端、Flutter 客户端。
> 背景：前一轮已把刷题时间 / 学习时间做进统计（`attempt.review_ms`，见 `architecture.md` §3.5「时长口径」）。本轮是五个相互独立的改进，只有「反馈处理」需要改服务端协议。

## 0. 总览

| # | 改造 | 改动面 | 协议 / 数据库变化 |
|---|---|---|---|
| 1 | 每日目标和提醒 | H5、Flutter | 无（目标存在本机设置里） |

- 两个客户端的行为保持一致（沿用此前 H5 先做、Flutter 随后对齐的做法），所以每一项下面都写了两端的落点。

## 1. 每日目标和提醒

### 1.1 现状

首页（题库列表）没有任何「今天做了多少」的信息；统计页的数据是按**单个题库**算的，没有跨题库的当日汇总。设置页只有服务器连接、同步、设备 ID。

### 1.2 要做什么

1. **设置页新增「学习目标」**：每天做 N 题（关闭 / 10 / 20 / 30 / 50 / 自定义）和每天学习 M 分钟（关闭 / 15 / 30 / 60 / 自定义）。两项都可以单独开关，都开时需**同时**达成才算完成。默认全部关闭，升级后不会冒出提示。
2. **首页顶部显示「今日进度」卡片**：已做题数 / 目标、已学分钟 / 目标，各一条进度条；达成后变成「今天的目标完成了」；没设目标时不显示这张卡。
3. **提醒**：设置里可开「每日提醒」并选时间（默认 20:00）。
   - **站内提醒**（两端都有）：到了提醒时间、目标没达成时，首页进度卡片变成醒目的「还差 X 题 / Y 分钟」。
   - **系统通知**：见 1.5，这一项受平台限制，需要你确认做到哪一步。
4. 目标只存在**本设备**（H5 的 `localStorage`，Flutter 的 `SharedPreferences`），不同步：手机和电脑可以有不同的目标。

### 1.3 「今日」怎么算

- 范围是**所有题库**（首页看的是全局），按本地自然日（0 点起）。
- 题数 = 今天的 `attempt` 条数（考试里作答的题也算，因为它们同样写进了作答记录）。
- 分钟 = 今天各条 `attempt` 的 `duration_ms + review_ms`，沿用统计页的封顶规则（单条答题最多 2 分钟、看解析最多 3 分钟），所以首页和统计页的「今天学习 X 分钟」口径一致。
- 同步下来的其他设备的作答也算（统计本来就是合并所有设备的）。
- 新增 `todayProgress(now)`：H5 在 `Repo` 里，Flutter 在 `Repository` 里；复用 `stats.ts` / `stats.dart` 里已有的封顶常量，把「单条记录折算多少毫秒」抽成一个共用函数，避免两处各写一份。

### 1.4 落点

| 端 | 文件 |
|---|---|
| H5 | 新增 `core/goals.ts`（读写目标、判断是否达成、提醒时间判断）；`data/repo.ts` 加 `todayProgress`；`views/BanksView.vue` 加进度卡片；`views/SettingsView.vue` 加「学习目标」区块 |
| Flutter | 新增 `core/goals.dart`（Riverpod provider + `SharedPreferences`）；`data/repository.dart` 加 `todayProgress`；`features/home/banks_page.dart` 加进度卡片；`features/settings/settings_page.dart` 加区块 |

### 1.5 提醒的平台限制（需要你拍板）

- **H5**：服务跑在局域网 HTTP 上，不是安全上下文，**浏览器通知 API 和 Service Worker 都不可用**（`architecture.md` §3.3 已记录同样的限制）。没有 Service Worker，页面关闭后也无法定时弹通知。所以 H5 能做到的是：**打开页面时**，如果过了提醒时间且目标没达成，就在首页显示提醒；如果将来上了 HTTPS（Tailscale `serve`），可以再加「打开页面时补发一条系统通知」，但仍然做不到「页面关着也准时提醒」。
- **Flutter**：要做到真正的定时系统通知，需要新增依赖（`flutter_local_notifications` + `timezone`），并改 Android 的权限（`POST_NOTIFICATIONS`、精确闹钟）与 Gradle 配置，macOS 还要处理通知权限。这是一块独立的平台工作，也要真机 / 模拟器验证。

**我的建议**：这一轮先做**站内提醒**（两端都有，零平台风险），把「系统定时通知」单独列为后续（只对 Flutter 有意义）。设置页里把提醒开关的说明写清楚——「打开 App 时提醒，不会在后台弹通知」，避免被误解。

### 1.6 测试

- 纯函数单测：目标达成判断（只开题数 / 只开分钟 / 两项都开）、跨午夜、提醒时间前后、没设目标。
- `todayProgress`：只算今天、封顶、合并多设备记录。
- 界面测试：设了目标后首页出现进度卡片，达成后文案变化；没设目标时不显示。

## 2. 按知识点刷题

### 2.1 现状

知识点只出现在两个地方：统计页的「知识点（薄弱的在前）」（只读）和模拟考试的出卷范围。想针对一个知识点练习，只能「专攻薄弱题」（最多 20 道、不分知识点）。

### 2.2 要做什么

1. **题库页新增「🏷️ 按知识点刷题」入口**，进入知识点列表页（`/bank/:id/topics`）。
2. 列表每行：知识点名称、题数、做过几题、正确率（没做过显示「未做」），按**题数从多到少**排；右上有「归类 / 细分」切换，沿用统计页和模拟考试同一套标签折叠规则（`tagLabeler`，归类时把「UML 辨析」并入「UML」）。
3. 点一行 = 随机刷这个知识点下的**全部题**；列表上方一个开关「只刷没做过的」和「只刷做错过的」（互斥，默认都关）。
4. **统计页的知识点行也可点击**，直接开始刷该知识点（用统计页当前的归类 / 细分状态），这样「发现薄弱 → 立刻练」一步到位。
5. 刷题进度**不保存**（`scope` 不传）：这是临时的专项练习，不应该覆盖题库的「继续上一轮」。

### 2.3 逻辑

新增纯函数 `quiz/topics.ts`（Flutter：`features/quiz/topics.dart`）：

```
topicQuestions(questions, label, merged): 该知识点下的题
topicSummary(questions, attempts, merged): [{label, count, answered, accuracy}]，按题数排序
```

- 取题和出卷范围用同一套规则：`paperPool` 现在用的就是归类后的标签，`topicQuestions` 直接复用它的标签映射，保证「知识点页」「统计页」「出卷」三处点同一个标签得到同一批题。
- 正确率沿用统计页口径：该知识点下所有作答次数中答对的比例。

### 2.4 落点

| 端 | 文件 |
|---|---|
| H5 | 新增 `quiz/topics.ts`、`views/TopicsView.vue`；`router.ts` 加 `/bank/:id/topics`；`BankView.vue` 加入口；`StatsView.vue` 的标签行改成可点 |
| Flutter | 新增 `features/quiz/topics.dart`、`features/home/topics_page.dart`；`banks_page.dart` 的题库详情加入口；`stats_page.dart` 的标签行改成可点 |

### 2.5 测试

- `topicQuestions`：归类前后取到的题不同、一题带多个标签只出现一次、大小写 / 全半角差异。
- `topicSummary`：没做过的知识点、单题多标签。
- 界面：点知识点行进入刷题，且题目都带该标签；「只刷没做过的」生效；统计页点标签行同样能开始。

## 3. 题库内搜索

### 3.1 现状

服务端有全文索引表 `question_fts`，但客户端没有搜索入口。客户端的题目全在本机（H5 的 IndexedDB、Flutter 的 SQLite），所以**搜索完全在本机做，离线也能用**，不需要新接口。

### 3.2 要做什么

1. **题库页新增「🔍 搜索题目」入口**（`/bank/:id/search`）。
2. 一个输入框，输入即搜（防抖 200ms）。**范围**：题干、选项、解析、知识点标签。
3. **多个词用空格分开，要求全部命中**（AND）；不区分大小写；全角 / 半角、多余空格先做规范化（复用 `normalizeTag` 同一套 `NFKC` 规整）。
4. 结果列表：题干（命中的词高亮）、题型、难度、知识点；如果命中在解析或选项而不在题干里，在下面多显示一行命中的片段，让人知道为什么搜到它。
5. 点一条 = 从这条开始刷整个搜索结果（`startQuiz(title, results, i)`，和错题本的行为一致）；顶部「练习这 N 道」按钮 = 随机刷全部结果。
6. 结果最多渲染 100 条，超出时显示「还有 X 条，请缩小范围」，避免一次渲染几千个节点。
7. 空关键词不搜；没有结果给出明确提示。

### 3.3 为什么不用 SQLite FTS

- 中文分词是 FTS5 默认分词器的弱项（逐字拆分，召回和排序都不好控制），而客户端题库规模是几百到几千题，直接做子串匹配足够快、结果也更符合直觉。
- 两端（IndexedDB 没有全文索引）能用同一套规则，行为一致。
- 如果将来题库大到子串匹配变慢，再在 Flutter 端换 FTS，H5 端保持现状。

### 3.4 逻辑

纯函数 `quiz/search.ts`（Flutter：`features/quiz/search.dart`）：

```
searchQuestions(questions, query): [{question, where: 'stem'|'option'|'explanation'|'tag', snippet}]
highlight(text, terms): 切成 [{text, hit}] 片段，供界面高亮
```

- 排序：题干命中的在前，其次选项 / 标签，最后解析；同级按题库原顺序。
- 高亮在 H5 里用片段数组渲染（不用 `v-html`，避免注入——题干来自模型，不可信）。

### 3.5 落点

| 端 | 文件 |
|---|---|
| H5 | 新增 `quiz/search.ts`、`views/SearchView.vue`；`router.ts`；`BankView.vue` 加入口 |
| Flutter | 新增 `features/quiz/search.dart`、`features/home/search_page.dart`；`banks_page.dart` 题库详情加入口 |

### 3.6 测试

- 多词 AND、大小写、全半角、空格、只命中解析的题、被下线（`hidden`）的题不出现。
- 高亮切片：多个词重叠、命中在开头 / 结尾、特殊字符（正则元字符不能当正则解释，用字面量匹配）。
- 界面：输入后出现结果、无结果提示、超过 100 条的提示。

## 4. 题目反馈的处理

### 4.1 现状（以及发现的问题）

客户端「反馈题目有问题」后，服务端 `FlagQuestion` 只做一件事：`flag_count + 1`，累计到 **2 次**（`flagThreshold`）就把题目改成 `needs_review`、备注写 `flagged by app users`，并推进 `sync_seq` 让所有设备下线这道题。

管理后台因此有这些缺口：

1. **看不全**：被反馈 1 次的题仍是「已发布」，后台没有任何地方能筛出它们；达到 2 次后才混进「待审核」，和新生成的题没法区分，只能靠备注文字猜。
2. **看不到原因**：服务端不记录谁、什么时候、为什么反馈，只有一个数字。
3. **没有「反馈不成立」的出口**：对被反馈下线的题点「通过」会重新发布，但**不会清零 `flag_count`**，于是下一次再有人反馈，计数立刻 ≥ 2，题目被立刻再次下线（实际是个 bug）。
4. **被反馈 1 次的题，在反馈的设备上被本机隐藏了，服务端却没有变化**，管理员即使认定没问题，也没有办法让那台设备把题找回来（找回只靠 `sync_seq` 推进）。

### 4.2 数据与接口

**迁移 00008：`question_flag` 表**（每一次反馈一行）

```sql
CREATE TABLE question_flag (
  id          TEXT PRIMARY KEY,                       -- ULID
  question_id TEXT NOT NULL REFERENCES question(id),
  reason      TEXT NOT NULL DEFAULT 'other',          -- wrong_answer | ambiguous | typo | other
  created_at  INTEGER NOT NULL,
  resolved_at INTEGER                                 -- 管理员处理后填写
);
CREATE INDEX idx_flag_question ON question_flag(question_id, resolved_at);
```

`question.flag_count` 的含义改为**未处理的反馈数**（处理后清零），不再是只增不减的总数。

**客户端上报**：`POST /api/v1/questions/{id}/flag` 增加**可选**请求体 `{"reason": "wrong_answer"}`。不带请求体的老客户端照常工作（原因记为 `other`）；未知的原因值按 `other` 处理。两端的反馈入口增加一个原因选择：「答案不对 / 题干有歧义 / 选项或文字有误 / 其他」。客户端的待上传反馈（H5 的 `flags` 存储、Flutter 的 `PendingFlags` 表）各加一个 `reason` 字段；Flutter 需要一次数据库升级（v4 → v5）。

**管理后台接口**

| 接口 | 作用 |
|---|---|
| `GET /admin/questions?flagged=1` | 筛出 `flag_count > 0` 的题，**不论状态**（已发布但被反馈的、已被自动下线的都在里面） |
| `GET /admin/questions/{id}`（已有） | 返回里增加 `flags: [{reason, created_at, resolved_at}]`，最新的在前 |
| `POST /admin/questions/{id}/dismiss-flags` | 「处理完毕」：把这道题的未处理反馈标记为已处理、`flag_count` 清零。若题目因反馈被自动下线（`needs_review` 且备注为 `flagged by app users`），同时**重新发布**；若题目是已发布状态，也**推进 `sync_seq`**，让被本机隐藏的设备把它找回来。其它原因造成的 `needs_review`（比如自动校验没过）不改状态，只清反馈 |

**对已有动作的修正**

- 「通过」（发布）和「驳回」都会**同时处理掉这道题的反馈**（标记已处理、`flag_count` 清零）。这修掉 4.1 的第 3 个问题。
- 「编辑」不自动清反馈：管理员改完题以后，需要明确点「处理完毕」，因为改动不一定解决了被反馈的问题。
- 自动下线的阈值（2 次）保持不变。

### 4.3 管理后台界面（`ReviewView.vue`）

- 状态筛选下拉新增一项 **「被反馈」**，旁边带数字角标（待处理的反馈题数），打开审核页就能看到有多少没处理。
- 题目列表行里，被反馈的题多显示一个红色标记「反馈 N」。
- 详情面板顶部，对有未处理反馈的题显示一条提示：**「N 位用户反馈了这道题：答案不对 ×2、题干有歧义 ×1」**，下面展开逐条（原因 + 时间）。
- 操作区新增按钮 **「处理完毕（保留）」**（`D` 快捷键），语义：我看过了，题没问题 / 我已经改好了，清掉反馈并让题目回到线上。
- 已有的「通过 / 驳回 / 编辑」保持不变，但对被反馈的已发布题，**「驳回」要能用**（现在已经可以：`published` 可驳回，驳回即下线）。

### 4.4 落点

| 位置 | 文件 |
|---|---|
| 服务端 | 迁移 `00008_question_flag.sql`；`db/queries/` 新增 `flag.sql`，`question.sql` 的列表 / 计数查询加 `flagged` 过滤；`service/sync.go`（`FlagQuestion` 记原因）、`service/review.go`（`flags`、`DismissFlags`、通过 / 驳回时清反馈）；`httpapi/` 新增路由；`api/openapi.yaml` |
| 管理后台 | `api/types.ts`、`api/client.ts`、`views/ReviewView.vue`；必要时 `utils/format.ts` 增加原因的中文名 |
| H5 | 反馈入口加原因选择（`views/QuizView.vue` 的菜单）；`data/repo.ts` 的 `flagQuestion` 带原因；`data/sync.ts` / `data/api.ts` 上传带原因 |
| Flutter | `features/quiz/quiz_page.dart` 反馈入口；`data/database.dart`（`PendingFlags.reason`，迁移 v5）、`repository.dart`、`sync_service.dart`、`api.dart` |

### 4.5 测试

- 服务端（`httpapi_test.go` / `service_test.go`）：不带请求体的老式反馈仍可用；带原因被记录；两次反馈自动下线；**下线后「通过」会清反馈，再被反馈不会立刻再次下线**；`dismiss-flags` 对三种状态（已发布且被反馈 1 次 / 因反馈下线 / 因校验未过下线）分别的行为；`flagged=1` 过滤；已处理的反馈不计入 `flag_count`。
- 客户端：反馈带原因进入待上传队列并被上传；老服务端（不认识 `reason`）仍然成功。
- 管理后台：筛选「被反馈」、详情里显示原因汇总、处理完毕后该题从筛选里消失（现有 `ReviewView` 没有界面测试，这一块用浏览器里走一遍来验证）。

### 4.6 升级注意

迁移 00008 启动时自动执行；它只**新增**一张表，不改旧表。已存在的 `flag_count` 数字保留（视为未处理），但没有对应的 `question_flag` 明细，后台详情里会显示「共 N 次反馈（无详细记录）」，管理员处理后清零。升级前照例备份数据库。

## 5. 错题本分题库

### 5.1 现状

错题本（H5 `/wrong`，Flutter 底部「错题本」页）把**所有题库**的错题混在一起，列表里也看不出每道题属于哪个题库。收藏页是同样的做法。

### 5.2 要做什么

1. 错题本页顶部增加**题库筛选**：「全部」+ 每个有错题的题库（带数量），默认「全部」，选择后只显示该题库的错题，「随机练习」也只练当前筛选范围。
2. 「全部」视图下，每一行显示所属题库名（小字），分清来源。
3. **题库页新增「📕 本题库错题本（N）」入口**，进入时直接定位到该题库的筛选（H5：`/wrong?bank=<id>`；Flutter：带 `bankId` 参数打开）；N = 0 时入口置灰或显示「没有错题」。
4. **收藏页同样处理**（共用同一个列表组件，顺手做掉，代价很小）。
5. 记住上次选的筛选：H5 存 `sessionStorage`，不跨会话——避免下次打开时以为「错题本空了」。
6. 刷题标题带上题库名（「错题本 · 软件设计师」），方便在刷题页和结果页分辨。

### 5.3 逻辑

- `Repo.wrongBook(bankId?)` / `favorites(bankId?)`：在现有按状态取题的基础上多一个可选的题库过滤；没有传就是全部（现有调用方——例如模拟考试「查漏补缺」读错题 id——不受影响）。
- 各题库的错题数由列表本身按 `bank_id` 聚合得到，不需要额外查询。
- 题库在服务端被删除 / 被下线、而本机还留着错题状态的情况：筛选条里用 `bank_id` 作兜底名字（「已删除的题库」），不丢数据。

## 6. 范围之外（本轮明确不做）

- 系统级定时通知（见 1.5，作为后续单独评估）。
- 跨题库的全局搜索（先做题库内；全局搜索需要在首页再放一个入口，等题库内版本用顺手了再说）。
- 反馈的自由文字说明（只做固定的几个原因，避免在手机上敲字）。
- 目标 / 提醒的跨设备同步。
- 复习队列 / 间隔重复（上一轮分析里的第一项，单独立项）。

## 7. 需要确认的几点（已按建议确认）

1. **提醒的范围**：本轮只做站内提醒（打开 App 时提醒），系统定时通知后续再说——可以吗？（1.5）
2. **目标的单位**：题数和分钟都做、可以单独开关——还是只要其中一个？（1.2）
3. **反馈原因**：加「答案不对 / 题干有歧义 / 选项或文字有误 / 其他」四选一，需要吗？不要的话反馈处理里只剩次数和时间，后台详情会简单一些。（4.2）
4. **错题本默认筛选**：默认「全部」，从题库页进入时才定位到该题库——还是默认定位到最近刷的题库？（5.2）
5. **收藏页**要不要一起分题库？（我建议一起做，成本很小。）

> 结论：1. 提醒只做站内提醒；2. 题数和分钟都做；3. 加反馈原因（四选一）；4. 错题本默认「全部」，从题库页进入才定位到该题库；5. 收藏页一起分题库。

## 9. 实现说明（与方案的差异和补充）

- **今日进度不算已下线的题**：`todayProgress`（Flutter 为 `watchDayProgress`）只算当前可见的题，和统计页同口径，所以首页数字与各题库统计页的「今天」之和一致；代价是反馈了一道题（它在本机被隐藏）后，今天的题数会少一条。
- **「只刷做错过的」＝曾经答错过**：不是「当前还在错题本里」，所以之后答对了、已移出错题本的题仍会出现，方便复习易错点。
- **对已发布但有反馈的题点「通过」**等同「处理完毕」（清反馈并推进 `sync_seq`），而不是空操作；批量通过同理。对已驳回的题点「处理完毕」只清反馈，不改状态。
- **`GET /admin/banks` 的 `question_counts` 多一个 `flagged` 键**（有未处理反馈的题数，可能与其它状态重叠），用来给管理后台的「被反馈」筛选做角标，没有改接口形状。
- **H5 的 IndexedDB 不用升级版本**：待上传反馈记录多一个可选的 `reason` 字段即可，旧记录读出来没有它，按不带原因上传。Flutter 的 `pending_flags` 加了一列，数据库 v4 → v5，有迁移测试。
- **Flutter 的搜索折叠规则略简单**：没有 NFKC，只折叠全角 ASCII 与全角空格再转小写；H5 用 NFKC。两端对常见输入（全角字母数字、大小写、多余空格）结果一致。
- **Flutter 错题本的「记住筛选」**靠页面在底部导航里常驻（App 退出即忘）；从题库页进入的是另一个单独的页面，不影响底部「错题本」页自己的选择。
- **提醒的时间**在 H5 页面开着时每 30 秒检查一次（Flutter 同），所以到点后最多晚 30 秒出现。
- **验证**：服务端 `go test -race ./...`、管理后台 `vue-tsc` 与 `vitest`、H5 `vitest`（168 条）与构建、Flutter `flutter test`（195 条）与 `dart analyze` 全部通过；管理后台的反馈流程（被反馈筛选、原因汇总、处理完毕后题目重新上线并从筛选里消失、重新上线后再被反馈只计 1 次）和 H5 的目标卡片、知识点页、搜索页、设置页在浏览器里对着一个临时服务器走过一遍。
